# CampusPulse RLS security audit

**Scope:** Static review of `supabase/migrations/202611260001_campuspulse_schema.sql`, `supabase/migrations/202611260002_campuspulse_rls.sql`, `supabase/migrations/202611260003_campuspulse_auth_bootstrap.sql`, and `docs/backend/rls-review.md`. This is not a live database test. Conclusions are based on source definitions and PostgreSQL/Supabase privilege and RLS semantics. The audit does not establish deployed grants, schema drift, execution results, storage policy behavior, or application/server endpoint behavior.

## Verdict

**PASS (static source review):** No confirmed high/critical RLS issue or migration blocker was found in the reviewed sources. All 20 schema tables appear in the RLS-enable/revoke loop; `auth.uid()` calls in SECURITY DEFINER helper bodies are explicitly qualified while the fixed `search_path = pg_catalog, public` is retained; report UPDATE access is limited to `resolution_note`; event club references are constrained to the event's college on INSERT and UPDATE; and the examined identity, college, grade, parent-visibility, cross-college, and faculty-course predicates do not reveal a high/critical bypass.

This verdict is limited to the reviewed source and is not a claim that migrations were applied or verified against a live database.

## Table and RLS coverage

The schema defines 20 application tables, all named in the migration's RLS-enable loop: `colleges`, `profiles`, `posts`, `comments`, `likes`, `saved_posts`, `follows`, `clubs`, `club_members`, `events`, `event_rsvps`, `notices`, `notifications`, `reports`, `courses`, `course_enrollments`, `assignments`, `assignment_submissions`, `rate_limits`, and `role_change_audit`. The loop enables RLS and revokes all table privileges from `anon` and `authenticated`; subsequent grants and policies selectively restore client access. `colleges`, `notifications`, `rate_limits`, and `role_change_audit` have no client policies. `colleges` and `notifications` have SELECT grants but remain denied by RLS; the other two have no client privileges. No table omission was found in the source inventory.

Policy coverage and principal conclusions:

| Data area | Static review conclusion |
|---|---|
| Profiles | Same-college/self SELECT and self UPDATE; UPDATE column grants are only `full_name`, `avatar_url`, and `bio`. Client changes to `role` or `college_id` are blocked. Bootstrap ignores requested role metadata and creates a student profile; requested college is checked against email domain. |
| Posts and children | Post visibility distinguishes public, same-college, and author-private rows. Comments, likes, and saves require a visible parent for relevant reads/inserts; self identity conditions prevent forging another user's child row. Parent visibility is enforced through the fixed-path SECURITY DEFINER helper. |
| Follows | Reads are restricted to same-college endpoints; inserts require the caller as follower and a same-college target. |
| Clubs/members | Club operations are same-college and faculty/admin gated. Self membership INSERT is constrained to `member`, with no client UPDATE policy to promote membership. |
| Events/RSVPs | Event access and role checks are own-college. INSERT and UPDATE require `club_id IS NULL` or a club whose ID and `college_id` match the event. RSVP writes must remain self-owned and target a same-college event. |
| Notices | Reads are own-college and audience-gated; writes are faculty/admin and own-college. Faculty/admin can edit rows in their college. |
| Reports | Self-only reporter INSERT and admin-only SELECT/UPDATE. Table UPDATE/DELETE is revoked; `resolution_note` alone is re-granted for UPDATE. `status`, `moderator_id`, and `resolved_at` are not client-updatable. |
| Courses/enrollments | Courses are visible only in the caller's college to students, assigned faculty, or admins. Faculty course INSERT/UPDATE/DELETE is tied to caller identity; UPDATE preserves `faculty_id=auth.uid()` and own college. Enrollments are self-visible or visible to the faculty assigned to that course, with no client write policies. |
| Assignments/submissions | Assignment writes are scoped through `is_faculty_of_course`; students see assignments for any course in their college, enrolled or not. Submission INSERT requires self and active enrollment with initial submitted/ungraded values. Own or assigned-faculty SELECT and assigned-course faculty UPDATE apply. Student-restricted columns include grade, status, feedback, student ID, and assignment ID; there is no student UPDATE policy. Own deletion requires submitted status and strictly before due date. |
| System tables | `notifications`, `rate_limits`, and `role_change_audit` are server-managed/inaccessible to client policies; client writes are revoked. |

## Required checks

- **`auth.uid()` qualification / fixed search path:** The helper function bodies use schema-qualified `auth.uid()`. `current_role()`, `current_college_id()`, `is_faculty_of_course()`, `is_admin()`, and `can_view_post()` retain fixed `search_path = pg_catalog, public`; function EXECUTE is revoked from PUBLIC/anon and granted to authenticated. No unqualified `auth.uid()` invocation was found in these helper definitions.
- **Narrow report UPDATE ACL:** The migration grants table UPDATE for reports earlier, then revokes table UPDATE/DELETE and grants only `UPDATE(resolution_note)`. Protected fields are additionally revoked. Under PostgreSQL column/table ACL semantics, admins satisfying the RLS policy can update only `resolution_note` through this client grant; they cannot change report status, moderator, resolved timestamp, or delete.
- **Event/club integrity:** Both event INSERT and UPDATE `WITH CHECK` expressions require a null club or an existing club with matching ID and college ID. UPDATE's `USING` additionally restricts source rows to the caller's college and faculty/admin role. This blocks cross-college club linkage through these policies.
- **Role/college/grade escalation:** Profile protected columns lack UPDATE grants. Course faculty ownership is held to the authenticated faculty ID and own college. Submission students cannot set grades/status/feedback on insert or update; faculty grading is scoped to the assigned course. No direct role, college, or student-grade escalation path was found.
- **Parent visibility:** Comment/like/save operations that read or attach to posts use `can_view_post`; its predicate permits public posts, same-college posts, or the author's private posts. A guessed child-row/post ID does not bypass that predicate.
- **Cross-college IDOR:** College-scoped table predicates and parent/course helper checks block the reviewed foreign-college IDs for non-public data. Public posts are intentionally readable to authenticated users across colleges. No unintentional cross-college direct row access was found in the reviewed policies.
- **Faculty course scope:** `is_faculty_of_course(course_id)` requires both `courses.faculty_id = auth.uid()` and course college equal to caller's college. Assignment/submission faculty access uses that helper; course-level faculty updates also preserve caller ownership and college.

## Residual medium findings

1. **Assignment visibility exceeds enrollment.** Any student in a college can read assignments for every course in that college, including courses where they are not enrolled. This is explicitly documented as intended in `docs/backend/rls-review.md`; **accepted by explicit design** in the reviewed source documentation. If assignments may contain non-public instructional material or answer-sensitive content, change the policy to require active enrollment.
2. **Course faculty can see all enrollment states for their course.** The enrollment SELECT policy includes assigned course faculty without filtering status. This is documented as the intended course-administration behavior in the backend review; **accepted by explicit design**.
3. **Admin audience semantics for notices are incomplete.** `notices_read_same_college_audience` includes the `students` and `faculty` branches only for those exact roles, so an admin cannot read a faculty-only or students-only notice (but can read `college`/`everyone`). This is an availability/semantics gap, not a confidentiality bypass. No explicit design statement confirms that admins should read role-specific audiences; treat as **not explicitly accepted** and confirm intended behavior.
4. **Club and notice updates are role/college-wide, not ownership-scoped.** Faculty/admin may update or delete any club or notice in their college. Club UPDATE can also change `owner_id` because the row check does not pin it. No cross-college or privilege-escalation path follows from this, and the policies explicitly implement a faculty/admin college-wide model; **accepted by explicit design as reflected in policy scope**, but consider ownership checks if narrower stewardship is intended.
5. **Report target validity is not checked at INSERT.** A user can submit a report with an arbitrary `target_type`/`target_id` pair; this can create nuisance or unresolvable reports, but does not grant access to the target or moderation data. **Not explicitly documented as accepted**; validate target existence/visibility in trusted logic if report quality matters.
6. **Faculty submission UPDATE can edit more than grading fields.** The table-level UPDATE grant plus faculty-scoped RLS permits course faculty to update submission fields beyond grade/feedback/status, including file metadata and timestamps (identity and assignment ID are revoked). The faculty principal is course-authorized, so this is not a student escalation or cross-course access issue; narrow faculty column grants if only grading is intended. **Not explicitly accepted.**

These medium items do not overturn the PASS verdict because no high/critical issue or migration blocker was identified in scope. Revisit the explicitly unaccepted semantics before production if they matter to product behavior.

## Migration and verification caveats

The RLS migration uses plain `CREATE POLICY` statements and is not safely rerunnable as-is against a database where those policies already exist; normal migration tracking should apply it once. The schema migration's `CREATE TABLE IF NOT EXISTS` does not reconcile existing schema drift, as its own header notes. No live database was available or tested. Before deployment, validate on a disposable Supabase/PostgreSQL instance, inspect effective ACLs and `relrowsecurity` for every table, test helper execution and representative adversarial probes, and reconcile existing schema/grant drift. Table owners and `service_role` can bypass RLS and must remain trusted/server-side. Storage and application/server endpoints are outside this audit.
