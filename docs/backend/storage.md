# Supabase Storage: file handling and access

## Buckets and limits

The forward migration `202611260004_storage_buckets_and_policies.sql` configures three buckets. All enforce a 25 MiB object limit (26,214,400 bytes) and an explicit bucket-level MIME allowlist. `avatars` accepts only `image/png` and `image/jpeg`; `post-media` and `assignments` accept `application/pdf`, `application/msword`, `application/vnd.openxmlformats-officedocument.wordprocessingml.document`, `image/png`, `image/jpeg`, `application/zip`, and `application/x-zip-compressed` (the latter accommodates clients that label ZIP files this way). Unsupported declared MIME types and oversized files are rejected by Storage. `avatars` is public-read, but authenticated writes are restricted to the caller's own folder. `post-media` and `assignments` are private; there are no public assignment links.

The bucket MIME setting and `storage.objects` row policies are defense-in-depth, not content inspection. A client can lie about a filename, extension, and `Content-Type`; MIME metadata is not proof of the bytes. The browser should sniff/validate the file signature before upload and reject files outside the supported formats, but client checks are bypassable. A trusted server-side validation/scanning step should inspect actual bytes (magic/signature and, where relevant, safely parse the document/archive) before accepting or serving untrusted files. Storage bucket MIME allowlists cannot do that, nor do they guarantee a file is harmless. Do not render untrusted HTML or active content inline. Consider malware scanning/quarantine before making uploads available.

## Object names and upload flow

Use UUID-based path components and a sanitized filename. Never concatenate user-provided path fragments without validation. A safe final filename should be generated by the client or trusted server from a random UUID plus an allowed extension, for example `c730...-uuid.pdf`; preserve the original display name separately in application metadata. The migration restricts path filename characters to ASCII letters/digits, dot, underscore, and hyphen, disallows `..`, and bounds filename length. Validate UUIDs and segment counts before issuing storage operations.

- **Avatar:** upload to `avatars/{authenticated_user_uuid}/{uuid}.{ext}`. Public reads are suitable only for intentionally public profile images; never put private material in this bucket. Owners can insert, update, and delete only under their own UUID folder.
- **Post media:** upload to `post-media/{post_uuid}/{uuid}.{ext}` after creating the post row. The caller must own that post to upload/change/delete its files. Authenticated reads use `public.can_view_post(post_uuid)`, so the post's current public/college/private visibility governs object access. Store the object path in the post's `media_urls` (or preferably a dedicated relation in a future schema); avoid storing public URLs. If visibility changes, object authorization follows the current post row.
- **Assignment submission:** the bucket ID is `assignments`, while `storage.objects.name` is bucket-relative. Use the explicit in-bucket prefix so the object name is `assignments/{course_uuid}/{assignment_uuid}/{student_uuid}/{uuid}.{ext}`; in the Supabase JS SDK this is `supabase.storage.from('assignments').upload('assignments/<course>/<assignment>/<student>/<uuid.ext>', file)`. Store that exact object name in `assignment_submissions.file_path`. `course_uuid` must match the assignment; the authenticated user must be the path's student and have an `active` `course_enrollments` row. Upload the object first, then insert `assignment_submissions` with the exact `file_path`, original display `file_name`, measured `file_size`, and declared `mime_type`. If the database insert fails, clean up the orphan object through an authorized cleanup flow. The submission table's file-size and MIME constraints provide additional metadata checks, not byte validation.

## Private object access and signed URLs

Use authenticated Storage SDK requests for private buckets; do not make `post-media` or `assignments` public, and never expose permanent/public assignment URLs. For downloads, the preferred API is an authenticated Edge Function (or trusted backend endpoint) that accepts a bucket and object path, validates the caller/session, queries the canonical post/submission and course relationship, and asks the Supabase server SDK to create a short-lived signed URL. For assignment files, authorize only the recorded `assignment_submissions.file_path`: the student owner or faculty of the offering's course. For post media, evaluate the current `can_view_post` visibility rules before signing. Return only a short expiry (for example, 60–300 seconds), avoid logging the URL, and do not cache it beyond its expiry. A signed URL is a bearer capability: anyone who obtains it can use it until expiry, and revoking a database/storage policy does not necessarily invalidate an already-issued URL. Keep the service-role key only in server-side secrets.

An alternative is to let authenticated clients download through the Storage API directly; policies then authorize object access at request time. Signed URLs are useful when application logic needs a controlled download handoff, but must be issued only after explicit server-side authorization. Do not use the service-role key in browser code.

## Policy boundaries and limitations

The assignment object `SELECT` policy requires a matching `assignment_submissions` row; access is granted to that row's student or the course's faculty. New student uploads require an active enrollment and exact path-to-assignment/course/user correspondence. Students can delete only a file recorded as their submission while its status is `submitted` and `now() < due_at`; this is deliberately true even when `allow_late` is enabled. Faculty can replace/update only a recorded submission belonging to their course. There is no faculty delete policy and no student overwrite policy; use a new UUID object and a separately authorized submission workflow for replacement rather than reusing a path. Assignment object insertion does not itself create or update a submission row.

Policies depend on the existing `public.can_view_post(uuid)` and `public.is_faculty_of_course(uuid)` helpers and existing course, enrollment, assignment, and submission tables. Test migrations and RLS in a disposable Supabase project, including an authenticated SDK upload using the exact prefixed in-bucket path above; confirm `storage.objects.name` and `assignment_submissions.file_path` both equal `assignments/<course>/<assignment>/<student>/<uuid.ext>`. Also verify malformed UUIDs in each of the course, assignment, and student positions and a key without the leading in-bucket `assignments/` segment are rejected, while the correctly structured enrolled-student path passes. Include simultaneous upload/submission operations and the chosen signed-URL route. This repository migration has not been applied to a live project. Signed URLs bypass subsequent per-request row-policy checks until their expiration; use short expiries and avoid issuing them before the submission row exists.
