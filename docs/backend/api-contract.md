# CampusPulse browser API contract

## Scope and setup

Implementation: [`campuspulse-frontend/public/api.ts`](../../campuspulse-frontend/public/api.ts), public TS declarations: [`campuspulse-frontend/public/api.d.ts`](../../campuspulse-frontend/public/api.d.ts). The module uses `@supabase/supabase-js` v2 and accepts an already-created `SupabaseClient`; it does not create clients, embed credentials, modify page scripts, or introduce a service-role key. Existing static screens and `app.js` are untouched. Import this module in a build/bundler and pass the authenticated client. The current frontend is a static prototype with no build/package setup, so the module is not wired into HTML.

Every database operation runs as the caller's authenticated session. RLS is authoritative; input helpers do not constitute authorization. `ApiResult<T>` is a discriminated union: success `{data:T,error:null}`, failure `{data:null,error:{message,code?,details?,hint?,status?}}`. Storage download returns the Supabase Storage response shape. Supabase policy, constraint, network and Edge Function errors are returned rather than suppressed. Invalid client-side size/MIME checks return the same error union. Authentication-dependent methods call `auth.getUser()`; missing user returns `Authentication required`.

The table contracts below match migrations `202611260001_campuspulse_schema.sql`, `202611260002_campuspulse_rls.sql`, and `202611260004_storage_buckets_and_policies.sql`. No live database was available; these are source-level mappings, not runtime-tested guarantees.

## Methods and table/policy mapping

| API | Tables / Storage | Inputs → outputs | Role and policy assumptions |
|---|---|---|---|
| `auth.profile()` | `profiles` | none → `Profile` | Authenticated self or same-college profile SELECT; own row is selectable even without college. |
| `feed.list({limit,after,author_id,visibility})` | `posts`, embedded `profiles` | limit 1–100 (default 20), optional cursor `{created_at,id}`, filters → `Page<Post>` | Authenticated; RLS returns only public, same-college, or own private posts. Embedded author relationship avoids per-post profile requests. |
| `posts.create({body?,media_urls?,visibility?})` | `posts` | content fields → `Post` | Authenticated author, current profile college; role unrestricted; same-college insert policy and DB body/media constraints. `author_id`/`college_id` are derived, not caller arguments. |
| `posts.update(id,input)`, `posts.remove(id)` | `posts` | id and editable content → `Post` / null | Owner only by RLS; updating `author_id` is not part of input. |
| `likes.set(post_id,enabled)`, `.list(post_id)` | `likes`, embedded `profiles` | post and boolean → null / rows | Any authenticated user can like/unlike a visible post, with user ID taken from session. Listing observes parent visibility. Unique pair makes set idempotent. |
| `saves.set(post_id,enabled)`, `.list(limit)` | `saved_posts`, embedded `posts` and post author | post and boolean → null / saved records | User's own saved rows only; post must currently be visible. |
| `comments.list(post_id,limit)`, `.create(post_id,body)`, `.update(id,body)`, `.remove(id)` | `comments`, embedded `profiles` | post/body/id → ordered rows / `Comment` / null | Authenticated; visible parent required; create attributes author from auth session; edit/delete own comments only. |
| `follows.set(following_id,enabled)`, `.list(user_id,direction)` | `follows`, embedded `profiles` | target, boolean; list target and `followers`/`following` → null / profile rows | Authenticated same-college users; self-follow rejected by DB constraint; insert only as current follower. |
| `clubs.list()` | `clubs`, embedded owner, `club_members` | none → club rows | Same-college club visibility. One embedded selection includes membership information (RLS may expose only permitted rows). |
| `clubs.join(club_id)`, `.leave(club_id)` | `club_members` | club → null | Join inserts only own `member` role; leave deletes only own row. Faculty/admin-created officer/owner memberships are not available through this client helper. |
| `clubs.create({name,description?})` | `clubs`, `profiles` | name/description → club row | `faculty` or `admin`; same-college; owner set to current user. Admin role policy permits club creation. |
| `events.list({from,limit})` | `events`, embedded `clubs`, `event_rsvps` | optional ISO lower-bound and limit → event rows | Same-college events. RSVP rows select policy is own-only, so the embedded list does not reveal other attendees. |
| `events.create(input)` | `events` | club/title/description/start/end/location/capacity → event row | Faculty/admin in same college; creator and college derived from current profile; club must be in same college. |
| `events.rsvp(event_id,status)` | `event_rsvps` | event and `going|interested|cancelled` → RSVP row | Authenticated same-college event, own RSVP only. `cancelled` is a status value and retains an RSVP row; use no delete helper. |
| `notices.list(limit)`, `.create(input)` | `notices`, embedded author on list | limit; title/body/audience/published/expiry → notice rows / new row | Reads filtered by RLS audience and college. Create is faculty/admin only; author and college derived from profile. |
| `reports.create({target_type,target_id,reason})` | `reports` | post/comment/user target and reason → report row | Any authenticated user can file as self. Reporter cannot read/update/delete client-side. |
| `reports.adminQueue(status?)` | `reports`, embedded reporter/moderator | optional status → report rows | Admin only by RLS. |
| `reports.setResolutionNote(id,resolution_note)` | `reports` | report ID/note → report row | Admin only; only resolution note is granted for update. This does not change status/moderator/resolved time. |
| `courses.list()` | `courses`, embedded faculty and enrollments | none → course rows | Same-college student can read all college courses; faculty sees own; admin same-college. Embedded enrollment visibility is limited by its own RLS (student's own or course faculty). |
| `courses.create({code,title,term})` | `courses`, `profiles` | code/title/term → course | Faculty creating own course only. Admin does not have the course insert policy. College and faculty derived from self profile. |
| `courses.enroll(course_id,student_id?)` | `course_enrollments` | course, optional student → enrollment row | With no `student_id`, inserts current user; policy has no client-side student INSERT rule in current migration, so this commonly fails unless another deployed policy exists. With `student_id`, course faculty helper authorizes only that course’s faculty. There is no self-enrollment rule in the SQL as written. This API does not bypass it. |
| `assignments.list(course_id?)` | `assignments`, embedded `courses` | optional course → assignments | Same-college students and course faculty may read. Enrollment is not required for reading. |
| `assignments.create(input)` | `assignments`, `profiles` | course/title/description/due/max points/late flag → assignment | Course faculty only; creator from current profile. Grade/status are not inputs. |
| `assignments.submissions(assignment_id)` | `assignment_submissions`, embedded student | assignment → submissions | Student sees own rows; course faculty sees submissions for their course. Admin is not automatically course faculty under this predicate. |
| `assignments.submitFile({assignment_id,course_id,file})` | private `assignments` bucket, then `assignment_submissions` | assignment/course IDs and browser `File` → `Submission` | Authenticated student must be actively enrolled; RLS validates exact pair, owner and initial `submitted`/null grade/null feedback. Upload first, then row. The literal object key is `assignments/{course_uuid}/{assignment_uuid}/{student_uuid}/{random}.{ext}` in bucket ID `assignments`, matching storage audit. Client enforces 1–25 MiB and allowed declared MIME; server checks remain authoritative and MIME is not byte validation. If row insert fails, private orphan may remain for trusted cleanup. |
| `assignments.download(file_path)` | private `assignments` Storage | canonical object key → Storage `{data:Blob,error}` | Storage RLS requires an exact submission row and owner or course faculty. Call only with a path returned from a submission row; never construct an arbitrary untrusted path. No public assignment URLs or client signing API. |
| `facultyDashboard()` | `courses`, `assignments`, `assignment_submissions`, embedded enrollments/course/student | none → `{courses,assignments,submissions}` | Explicit frontend guard requires faculty/admin; queries scope records to current faculty ID. Admin dashboard data beyond own faculty-owned courses will be empty/limited; submission RLS still restricts to course faculty. Parallel embedded queries avoid per-course/per-submission N+1. |
| `ai(body,functionName='campuspulse-ai')` | Supabase Edge Function invocation | JSON object and optional deployed function name → generic function result | Requires authenticated user. Function is expected to validate auth, authorization and input server-side, apply rate limits, and protect any model secrets. No `campuspulse-ai` Edge Function is present in this repository; deployment must provide it. |

## Feed keyset pagination

Feed order is newest-first with deterministic `created_at DESC, id DESC`, and the next page predicate is `(created_at,id) < (cursor.created_at,cursor.id)`. The query requests `limit+1`, returns up to `limit`, and sets `next` to the last returned row only if another row exists. Pass that cursor unchanged to the next `feed.list` call. This avoids offset drift and pairs with schema index `posts_college_feed_idx (college_id, created_at DESC, id DESC)` plus RLS visibility filtering. A page can be shorter where policy filtering applies. Never manufacture cursors from client-local timestamps.

## Security and known policy gaps

- Roles are database profile attributes, not trusted caller input. Auth bootstrap deliberately ignores role metadata and creates students. Only backend/admin provisioning should grant roles; the module has no role setter.
- Client method inputs omit protected IDs where safely derivable, and submission inputs never accept `status`, `grade`, or `feedback`. Student submission insert has DB policy/column constraints enforcing initial state; faculty grading is not exposed as a convenience helper. The migration revokes authenticated updates to protected submission columns. Do not add those columns to a client update payload.
- `courses.enroll` accurately surfaces the migration gap: no student self-enroll INSERT policy exists. Faculty can enroll a specified student using `is_faculty_of_course`. Do not interpret a failed self-enrollment as a client bug or work around it.
- Reports cannot be read by their reporter; status and moderator fields are server/admin-controlled. Notice, event and course roles have different policy capabilities; frontend visibility is not authorization.
- Assignment uploads are private, with 25 MiB storage limit. The path and saved `file_path` must be identical. Policy relies on `active` enrollment; late submission enforcement is not in the insert policy shown here, and clients cannot set grading fields. DB/file metadata do not validate bytes. The storage audit notes orphan uploads if the subsequent row insert fails and recommends a trusted cleanup flow.
- Current RLS grants no client insert/update/delete to notifications, rate limits or role audit, and no policy-backed client colleges directory query. This module intentionally provides no methods for them.
- Supabase relationship aliases use declared FK relationships. If generated DB types or FK names change, regenerate/review selects. Embedded selects reduce round trips; no helper loops through rows to issue per-row queries.
- The frontend may display temporary likes/bookmarks/RSVPs today. This module does not alter `app.js` or HTML; integration is a separate authorized change.
